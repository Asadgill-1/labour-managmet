# T20d-c: getting the cloud copy back

**Goal:** a company that lost its phone sees its cloud copies on the new one, buys the add-on with a slip, and brings a copy back through the restore it already knows.

**Spec:** `docs/superpowers/specs/2026-11-14-t20d-cloud-backup-design.md`. The cloud's contract is in `docs/superpowers/plans/2026-11-14-t20d-a-cloud.md`. Decisions D-072, D-075, D-076, D-077; this slice's calls go in D-078.

**Built by:** this session, task by task, with a self-review at the end (the owner's standing choice).

## Constraints

- No change to the cloud: T20d-a's functions and tables are used as built.
- The app keeps working against a live project that has not run T20d-a's migration yet: a slip for the plan alone sends no `p_covers`, and the slips are read without naming the `covers` column.
- Money in integer fils (CALC-01). The app shows what a slip will cost; the cloud works out what it expects.
- Never called end-to-end encrypted (DATA-08). A build without the recovery key offers neither the cloud list nor the add-on.
- Nothing runs on the live project.

## Review focus

- The old phone is still on: the new phone gets `other_phone` on the download. It must say so and lead to the phones list, not look like a missing add-on.
- The swap fails after a cloud copy was prepared: the next copy must not go with `replace`, or the old data here would take the other phone's place unasked.
- An older daily copy brought back, not the newest: `replace` would drop the other phone's latest copy unseen, so the question stays.
- The add-on bought, the slip accepted, the licence on the phone still the old one: the list must ask the cloud again before saying the add-on is missing.
- A session the cloud no longer takes on the list: the password is asked, nothing is lost.
